# Qdrant-сервис синхронизации

Сервис для периодической синхронизации данных из ClickHouse (auction_vectors) в Qdrant. Поддерживает историческую заливку и инкрементальное обновление на основе поля updated_at.

## Назначение

Проект предназначен для:
- Исторической заливки всех кластеров пользователей в Qdrant при первом запуске.
- Инкрементального обновления изменившихся пользователей (по полю updated_at).
- Поддержания актуального состояния векторов для поиска похожих пользователей.
- Логирования операций синхронизации в PostgreSQL.

## Архитектура

Проект состоит из следующих компонентов:

- `app.py` — точка входа (шедулер).
- `runner.py` — запуск синхронизации.
- `uploader.py` — основная логика синхронизации (историческая/инкрементальная).
- `clickhouse.py` — работа с ClickHouse (чтение данных).
- `postgres_logger.py` — логирование в PostgreSQL.
- `settings/` — конфигурация и логгер.

## Как работает

1. Сервис стартует и инициализирует подключения к ClickHouse, Qdrant и PostgreSQL.
2. Проверяются доступность БД и создаются таблицы (qdrant_sync_state, qdrant_sync_log).
3. Шедулер запускает `run_qdrant_sync()` с заданным интервалом.
4. Синхронизация:
   - Проверяет существование коллекции в Qdrant.
   - Если коллекции нет — выполняет историческую заливку всех кластеров.
   - Если коллекция существует — выполняет инкремент:
     - Находит пользователей с `updated_at > last_sync_time`.
     - Удаляет их старые точки из Qdrant.
     - Загружает актуальные кластеры из ClickHouse.
     - Вставляет их в Qdrant.
     - Обновляет `last_sync_time`.
   - Логирует результат в PostgreSQL.

## Обработка данных

### Историческая заливка (`historical_upload`)

- Удаляет коллекцию, если она существует, и создаёт заново.
- Загружает все кластеры из auction_vectors через `fetch_all_clusters`.
- Вставляет точки в Qdrant батчами (размер настраивается).
- Обновляет `last_sync_time` до максимального `updated_at`.

### Инкрементальная синхронизация (`incremental_upload`)

- Получает `last_sync_time` из таблицы состояния.
- Находит пользователей с `updated_at > last_sync_time`.
- Для каждого батча пользователей:
  - Определяет, у кого есть кластеры (через `get_users_with_clusters`).
  - Удаляет пользователей без кластеров из Qdrant.
  - Для остальных удаляет старые точки и загружает актуальные.
- Обновляет `last_sync_time` до максимального `updated_at` среди обработанных.

### Повторные попытки

- При ошибках Qdrant (таймауты, 400/500) делается до 3 попыток с экспоненциальной задержкой (1, 2, 4 сек).
- При успехе — продолжается, при трёх неудачах — исключение.

## Таблицы PostgreSQL

- `qdrant_sync_state` — состояние синхронизации.

| Поле | Тип | Описание |
|------|-----|----------|
| collection_name | String | Имя коллекции в Qdrant |
| last_sync_time | DateTime64(9, 'UTC') | Время последней успешной синхронизации |
| updated_at | DateTime64(9, 'UTC') | Время обновления записи |

- `qdrant_sync_log` — история запусков синхронизации.

| Поле | Тип | Описание |
|------|-----|----------|
| id | SERIAL | Первичный ключ |
| runner_start | TIMESTAMPTZ | Время начала синхронизации |
| runner_end | TIMESTAMPTZ | Время окончания |
| data_json | JSONB | Метрики (операция, количество точек, время по этапам) |
| errors | TEXT | Текст ошибки (если была) |

## Ключевые оптимизации

- **Массовое удаление** — пользователи удаляются батчами (100 за раз).
- **Потоковая загрузка** — данные из ClickHouse читаются и сразу отправляются в Qdrant.
- **Повторные попытки** — при ошибках Qdrant делается до 3 попыток с экспоненциальной задержкой.
- **Профилирование** — детальные замеры времени по этапам.

## Профилирование

В логах фиксируются:
- `find_time` — время поиска обновлённых пользователей.
- `delete_time` — суммарное время удаления точек.
- `load_time` — суммарное время загрузки новых точек.
- `update_time` — время обновления `last_sync_time`.
- `total_time` — общее время инкремента.
- `users_found` — количество найденных пользователей.
- `total_points` — количество загруженных точек.

## Требования

- Python 3.9+
- ClickHouse (источник auction_vectors)
- Qdrant (локальный или удалённый)
- PostgreSQL (логи)
- Установленные зависимости из `requirements.txt`
